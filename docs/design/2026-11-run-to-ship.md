# 設計の承認後は PR 作成の直前まで止まらずに進める

- Status: Approved
- 作成日: 2026-11-06
- 関連 ADR: docs/adr/0009-design-principles.md、docs/adr/0013-no-approval-within-approved-plan.md（Superseded にする）、docs/adr/0014-run-to-ship-after-approval.md（T1 で起票）

## 1. 背景と目的
- 別のプロジェクトで sdd 0.6.0 を使ったとき、設計書を承認したあとも、Claude がタスク（T1・T2）を 1 つ終えるたびに止まって「次に進めてよいか」と聞いた。
- 0.6.0（ADR 0013）では、design の SKILL.md・CLAUDE.md のテンプレートのルール 7・guide の 2-D に「タスクの間で確認しない」と書いてある。それでも止まった原因は次のとおり。
  - 承認を「事前の許可」とみなす、と書いていない。そのため、ユーザー設定の「変更の前に許可を得る」「小さく段階的に進める」が優先された。
  - 承認したあとに何がどこまで進むかが、設計書の本文に無い。承認の時点でユーザーに伝わらず、要約のあとに読み直すこともできない。
  - 実装が終わったあとに `/sdd:ship` を Claude が自分で起動する、と書いていない。「reaches commit and PR で止まる」では、ship の前で止まるのか 3-7 で止まるのかがはっきりしない。
  - 止まる場面の書き方が、場所ごとに少しずつ違う。
- 成功の定義：区分 A・B・C のどれでも、計画を承認したあとは、止まる場面の一覧に当たらないかぎり `/sdd:ship` の 3-5 まで止まらずに進み、PR の前（3-7）で 1 回だけ確認を求める。ユーザー設定に「変更の前に許可を得る」とあっても、この動きは変わらない。

## 2. スコープ
- やること:
  - design のテンプレートに「承認後の進め方」の節を足し、止まる場面の一覧の正本にする。
  - design・ship の SKILL.md、CLAUDE.md のテンプレートのルール 7、guide.md、README（英・日）を直す。
  - タスクの区切りで、作業ブランチにローカルでコミットする（push はしない）。
  - ADR 0014 を起票し、ADR 0013 を Superseded にする。plugin.json を 0.7.0 にし、CHANGELOG.md に追記する。
- やらないこと（Non-goals）:
  - タスクの区切りでの push。push は 3-7 の承認のあとに、PR の作成と一緒に行う。
  - 権限の設定やフックで止まらないようにすること（権限の確認と承認の問いかけは別のもの。ADR 0013 の検討どおり）。
  - adr の SKILL.md の保存の規則の変更（計画のタスクにある ADR は確認なしで保存、それ以外は承認を得る、のまま）。
  - このリポジトリ自身の CLAUDE.md の変更。
  - スキル・エージェントの追加と削除（数は 6 のまま）。

## 3. 要件
- REQ-1: design のテンプレートの「5. Implementation tasks」の最後に「After approval」の節があること。そこに、承認の範囲と止まる場面の一覧を書くこと。この一覧が正本である。
  - 承認の範囲：計画を承認すると、そのあと止まらずに T0 → T1…Tn（各タスクのあとにテスト・lint・型チェック、通ったら作業ブランチにコミット）→ `/sdd:ship` の 3-1〜3-5 まで進む。この承認は、計画の範囲の変更への事前の許可とみなす。ユーザーの設定や CLAUDE.md に「変更の前に許可を得る」とあっても同じ。
  - 止まって確認する場面（これだけ）：
    1. ADR の案の承認。計画のタスクに無い判断を記録するとき、または既存の ADR を Superseded にするとき。
    2. Accepted な ADR に反する変更が必要になったとき。
    3. 要件が足りないか矛盾しているとき。または、計画の範囲を超える変更が必要になったとき（区分の格上げを含む）。
    4. テストが通らず、設計を変えないと直せないとき。
    5. 本番への書き込み、外部への公開、push など、取り返しのつかない操作や外に見える操作が必要なとき（3-6 は人間が行う）。
    6. `/sdd:ship` の最後の push と PR の作成の前（3-7）。
  - 上の場面では、遠慮せずに止まって確認する。止まらずに進めるのは確認の要らない作業だけで、確認すべきことを飛ばしてよいという意味ではない。
  - コミットは、作業ブランチにローカルで行う。デフォルトブランチにいるときは、最初のコミットの前に作業ブランチを作る。git の管理下にないときはコミットしない。
- REQ-2: design の SKILL.md が次のとおりであること。
  - ステップ 1：計画を承認に出すときに、承認のあとに何がどこまで進むか（PR の前まで止まらずに進むこと、止まる場面は計画の「After approval」の節にあること）を 1〜2 文で添える。
  - ステップ 2：T0 のあとは止まらずに T1 へ進む。「After approval」の節に従う。承認を事前の許可とみなすことを明記する。全部のタスクが終わったら `/sdd:ship` を起動する。
  - 止まる場面の一覧は SKILL.md に重ねて書かず、節を参照する。
- REQ-3: ship の SKILL.md が次のとおりであること。
  - 実装のタスクのあとに起動されたときは、ステップ 0〜5 を止まらずに続けて行う（止まるのは計画の「After approval」の節の場面だけ）。
  - ステップ 6：残りの変更を作業ブランチにコミットする。タスクの区切りのコミットと合わせて変更を見せ、3-6 が必要なら先に済ませるよう添える。承認を得てから push と PR の作成を行う。push と PR の作成の前には必ず承認を得る。
- REQ-4: CLAUDE.md のテンプレートのルール 7 が、設計書の無い計画（区分 B・C）でも REQ-1 と同じ動きになること。承認は事前の許可とみなす。タスクの区切りでコミットする。`/sdd:ship` を 3-5 まで進める。止まる場面は、設計書があれば「After approval」の節、無ければ同じ一覧を短く書く。
- REQ-5: guide.md の 2-A・2-C・2-D・3 が、上の動きと矛盾せず、止まる場面については design のテンプレートの節を参照すること。guide.md は 160 行以下であること。
- REQ-6: README.md と README.ja.md の Notes が、同じ内容で上の動きを説明していること（承認の範囲、タスクごとのコミット、push と PR は承認のあと）。
- REQ-7: ADR 0014 が Accepted で、決定と、不採用の代替案とその理由が書かれていること。ADR 0013 の Status が `Superseded by 0014` であること。
- REQ-8: plugin.json の version が 0.7.0 で、CHANGELOG.md に 0.7.0 が書かれていること。変更したスキルの `reviewed` が実施日であること。
- 非機能要件:
  - 予算：スキル＋エージェントは 6 のまま。guide.md は 160 行以下。`bash .github/scripts/check-principles.sh` が 0 で終わること。
  - 検証：`claude plugin validate --strict .` と `bash .github/scripts/check-public-files.sh` が通ること。スキルから `..` を含むパスやシェル展開で、スキルのディレクトリの外を読まないこと（ADR 0006）。
  - 互換性：`- Status:` の行、REQ-n、`- [ ]` の Tn の形は変えず、ask・ship・verifier の判定を変えないこと。ship の区分の判定は、タスクの区切りのコミットも `<default branch>...HEAD` で拾うので、変えなくてよい。

## 4. 設計
- 正本の場所：止まる場面の一覧は design のテンプレート（`plugins/sdd/skills/design/template.md`）の「After approval」の節に置く。
  - 理由：スキルは自分のディレクトリの外を読めない（ADR 0006）。そのため、design と ship から ask の guide.md は参照できない。また、guide.md は `/sdd:ask` のときしか読まれない。テンプレートの節は、すべての設計書の本文に写されるので、コンテキストが要約されたあとでも読み直せる。承認の時点で、ユーザーの目にも入る。
  - 設計書の無い区分 B・C では、CLAUDE.md のルール 7 に同じ一覧を短く書く。テンプレート側の正本と、ルール 7 の 2 か所になる。ずれは §6 の grep で確かめる。
  - SKILL.md（design・ship）と guide.md は、一覧を重ねて書かず、節を参照する。
- 承認と許可：承認を「計画の範囲の変更への事前の許可」とみなすと書く。ユーザーの「変更の前に許可を得る」に反するのではなく、計画の承認がその許可に当たる、という位置付けにする。
- コミット：タスクの区切りでローカルにコミットする。手元だけの操作なので取り消せるし、タスクごとの区切りが履歴に残る。push は外に見える操作（CI も動く）なので、3-7 の承認のあとに PR の作成と一緒に行う。
- ship の自動起動：ship は `disable-model-invocation: false` なので、Claude が起動できる。design の SKILL.md・ルール 7 から「全部のタスクが終わったら `/sdd:ship` を起動する」と指示する。
- 純正で代替できない理由：スキルの追加は無い。既存のスキル・テンプレート・文書の中だけで直す。
- 検討した代替案と不採用の理由（ADR 0014 に記録する）:
  - 正本を guide.md に置く：実装中に読まれないので、各 SKILL.md に同じ文を書くことになり、ずれる。
  - タスクの区切りで push もする：外に見える操作が、確認なしで何度も起きる。PR の前の 1 回の確認で足りる。
  - コミットも 3-7 までしない（現状）：タスクの区切りが履歴に残らず、途中でやり直すのが難しい。
  - 区分 A だけに適用する：B・C でも、計画の承認のあとに止まる問題は同じように起きる。
