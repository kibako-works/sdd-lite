# 0014. 承認後は PR の作成の前まで止まらずに進め、止まる場面の正本を design のテンプレートに置く

- Status: Accepted
- 日付: 2026-11-06
- 関連: docs/design/2026-11-run-to-ship.md、docs/adr/0013-no-approval-within-approved-plan.md（これを置き換える）、docs/adr/0009-design-principles.md

## Context（背景）
- ADR 0013 で、承認済みの計画の中ではタスクの間で確認しない、と決めた。それでも別のプロジェクトでは、設計書を承認したあとに、Claude がタスクを 1 つ終えるたびに止まって「次に進めてよいか」と聞いた。
- 原因は次のとおり。
  - 承認を「事前の許可」とみなす、と書いていなかった。そのため、ユーザー設定の「変更の前に許可を得る」が、承認済みの範囲にも当てはめられた。
  - 承認したあとに何がどこまで進むかが、設計書の本文に無かった。承認の時点でユーザーに伝わらず、コンテキストが要約されたあとに読み直すこともできなかった。
  - 実装が終わったあとに `/sdd:ship` を自分で起動する、と書いていなかった。ADR 0013 の「コミット・PR のときは止まる」は、ship の前で止まるとも読めた。
  - 止まる場面の書き方が、design の SKILL.md・CLAUDE.md のテンプレート・guide で少しずつ違った。
- スキルは自分のディレクトリの外を読めない（ADR 0010）。そのため、design と ship から ask の guide.md は参照できない。guide.md は `/sdd:ask` のときしか読まれない。

## Decision（決定）
- 計画（design doc、または Plan Mode の計画）の承認を、計画の範囲の変更と、`/sdd:ship` の 3-1〜3-5 までへの事前の許可とみなすこと。ユーザーの設定や CLAUDE.md に「変更の前に許可を得る」とあっても同じとすること。
- 承認したあとは、T0 → T1…Tn（各タスクのあとにテスト・lint・型チェック）→ `/sdd:ship` の 3-5 まで、止まらずに進めること。全部のタスクが終わったら、Claude が `/sdd:ship` を起動すること。
- 止まって確認するのは、次の場面だけとすること。これらの場面では、遠慮せずに止まること。
  1. ADR の案の承認（計画のタスクに無い判断を記録するとき、既存の ADR を Superseded にするとき）
  2. Accepted な ADR に反する変更が必要になったとき
  3. 要件が足りない・矛盾しているとき、計画の範囲を超える変更が必要になったとき（区分の格上げを含む）
  4. テストが通らず、設計を変えないと直せないとき
  5. 本番への書き込み、外部への公開、push など、取り返しのつかない操作や外に見える操作が必要なとき
  6. `/sdd:ship` の最後の push と PR の作成の前（3-7）
- タスクの区切りで、テストが通ったら作業ブランチにローカルでコミットすること。デフォルトブランチにいるときは、最初のコミットの前に作業ブランチを作ること。push はしないこと。git の管理下にないときはコミットしないこと。
- 止まる場面の一覧の正本は、design のテンプレートの「After approval」の節に置くこと。design と ship の SKILL.md と guide.md は、一覧を重ねて書かずに、この節を参照すること。設計書の無い計画のために、CLAUDE.md のテンプレートのルール 7 にだけ、同じ一覧を短く書くこと。

## Consequences（結果）
- 区分 A・B・C のどれでも、承認したあとに止まるのは、上の場面と PR の前の 1 回になる。
- 承認の範囲が設計書の本文に残るので、承認の時点でユーザーに伝わり、要約のあとでも読み直せる。
- タスクごとのコミットが作業ブランチに残る。PR の前の確認では、コミット済みの変更も合わせて見せる必要がある。
- 一覧は、テンプレートとルール 7 の 2 か所に書かれる。変えるときは両方を直し、grep で同じ 6 項目であることを確かめる。
- ルール 7 は、新しく作る CLAUDE.md と節ごと追記する CLAUDE.md にだけ入る（ADR 0013 と同じ）。既存の「Development flow」を持つ利用者は、手で直す必要がある。
- 検討した代替案と、採らなかった理由:
  - 正本を guide.md に置く：実装中に読まれないので、各 SKILL.md に同じ文を書くことになり、ずれる。
  - タスクの区切りで push もする：外に見える操作（CI の実行を含む）が、確認なしで何度も起きる。PR の前の 1 回の確認で足りる。
  - コミットも 3-7 までしない（ADR 0013 のまま）：タスクの区切りが履歴に残らず、途中でのやり直しが難しい。
  - 区分 A だけに適用する：B・C でも、計画を承認したあとに止まる問題は同じように起きる。

## 検証方法（任意）
- `grep -n 'After approval' plugins/sdd/skills/design/template.md` で節が見つかり、`grep -rn 'After approval' plugins/sdd/skills/` で design・ship の SKILL.md、CLAUDE.md のテンプレート、guide.md から参照されていること。
- テンプレートの節と CLAUDE.md のテンプレートのルール 7 の止まる場面が、同じ 6 項目であること。
