# 0013. 承認済みの計画の中では確認を求めない

- Status: Accepted
- 日付: 2026-11-02
- 関連: docs/design/2026-11-trial-feedback.md、docs/adr/0009-design-principles.md、docs/adr/0012-design-as-plan-form.md

## Context（背景）
- ADR 0009 の原則 1 は「人間の承認は設計と PR の 2 回まで」である。
- kome-oroshi-app での試験運転（2026-11-02）では、区分 A の流れで、計画の承認のほかに 7 回止まった。ユーザーからは、タスクごとの確認や「次に進んでよいですか？」が非常にストレスだった、という声があった。
- 止まった理由は次の 3 つだった。
  - adr の SKILL.md と guide の §2-A の 6 が、承認済みの計画に入っている ADR のタスクにも、保存の前の承認を求めていた。
  - CLAUDE.md のテンプレートに、承認のあとは止まらずに進める、という指示が無かった。そのため、確認を求めたり、追加の作業を持ちかけたり、答えた問いをもう一度聞いたりする、モデルの癖がそのまま出た。
  - init が既存の CLAUDE.md に Common commands を追記しなかった。そのため、セットアップのあとに追加の確認が要った。
- guide は `/sdd:ask` を実行したときしか読まれない。一方、CLAUDE.md は毎回のセッションで読まれる。

## Decision（決定）
- 承認済みの design doc か Plan Mode の計画に入っている ADR のタスクは、`/sdd:adr` で確認を求めずに保存すること。中身は PR の差分で確認する。
- 単独の ADR（2-B）、実装中に新しく出た判断、既存の ADR を Superseded にするときは、今までどおり案を見せ、承認を得てから保存すること。
- CLAUDE.md のテンプレートの「Development flow」に、「承認のあとはタスクの間で確認せずに最後まで進める」行を置くこと。止まってよいのは次のときだけとする。
  - 計画からはずれたとき
  - Accepted な ADR とぶつかったとき
  - 人間にしかできない確認があるとき
  - コミット・PR のとき
- `/sdd:design` も、承認のあとの手順として同じ決まりを持つこと。
- 確認なしで保存してよいかは、承認済みの計画のタスクがその判断を ADR として記録すると書いているかで決めること。タスクに無い判断は、計画の実行中でも承認を得ること（計画ファイルに残るので、clear context のあとも判断できる）。

## Consequences（結果）
- 区分 A の流れで止まるのは、計画の承認と PR の承認の 2 回になる。
- 計画の中の ADR は、PR まで人間の目を通らない。中身が計画とずれていれば、PR の差分で見つけて直す必要がある。
- 区分 A の流れでは、`/sdd:design` が決まりを持つので、既存の CLAUDE.md でも効く。テンプレートの行は、新しく作る CLAUDE.md と節ごと追記する CLAUDE.md にだけ入るので、区分 B・C の計画にも効かせるには、既存の「Development flow」に手で足す必要がある。
- 検討した代替案と、採らなかった理由:
  - adr の承認をすべて無くす：単独の ADR（2-B）は設計の承認に当たるので、設計の承認が 0 回になる。
  - テンプレートには書かず、guide にだけ書く：guide は ask のときしか読まれないので、実装中のモデルの癖には効かない。
  - フックや権限の設定（auto mode など）で止まらないようにする：権限の確認と、承認の問いかけは別のものである。また、純正の設定を利用者に強いることになる。

## 検証方法（任意）
- `grep -n 'approved plan\|approved design doc' plugins/sdd/skills/adr/SKILL.md` で、計画のタスクの場合の分岐が見つかること。
- `grep -n 'without asking' plugins/sdd/skills/init/claude-md-template.md` で、テンプレートの行が見つかること。
