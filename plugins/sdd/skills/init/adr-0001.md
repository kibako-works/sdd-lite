# 0001. Record decisions with ADRs

- Status: Accepted
- Date: YYYY-MM-DD
- Related: none

## Context
Over time, the reasons behind design decisions get lost. Both new human contributors and AI agents may make changes that go against existing decisions without knowing why they were made. We want to keep the reasons for decisions in the repository, readable as context for future development.

## Decision
- When you make a technology choice, a structural change, or a decision with trade-offs, record an ADR in docs/adr/, one file per decision.
- Write ADRs in the Michael Nygard format (Context / Decision / Consequences), and name files `NNNN-<slug>.md` (sequential numbers).
- Don't implement anything that goes against an ADR whose Status is Accepted.
- If a change contradicts an existing ADR, record a new ADR and mark the existing ADR as Superseded before implementing.
- Don't rewrite the Decision of an ADR once it is Accepted; make changes with a new ADR.

## Consequences
- The background of decisions stays in the repository, available to both humans and AI agents.
- Writing an ADR for each decision takes extra effort.
- ADRs are plain Markdown, so they don't depend on any particular tool and remain readable if you move to other tools.

## Verification (optional)
- Sequentially numbered ADRs exist in docs/adr/, and each ADR states its Status.
- PRs that include design decisions link to the corresponding ADR.
