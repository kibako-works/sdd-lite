# 0001. ADR で判断を記録する

- Status: Accepted
- 日付: YYYY-MM-DD
- 関連: なし

## Context（背景）
設計上の判断は、時間が経つと「なぜそうしたか」が失われる。人間の新規参加者も AI エージェントも、過去の判断の理由を知らないまま、既存の決定に反する変更をしてしまうおそれがある。判断の理由をリポジトリ内に残し、次の開発の文脈として読める状態にしたい。

## Decision（決定）
- 技術選定・構造変更・トレードオフのある判断をしたら、docs/adr/ に ADR を1判断1ファイルで起票すること。
- ADR は Michael Nygard 形式（Context / Decision / Consequences）で書き、ファイル名は `NNNN-<slug>.md`（連番）とすること。
- Status が Accepted の ADR に反する実装をしないこと。
- 既存 ADR と矛盾する変更が必要な場合は、実装前に新しい ADR を起票して既存 ADR を Superseded にすること。
- 一度 Accepted にした ADR の Decision は書き換えず、変更は新しい ADR で行うこと。

## Consequences（結果）
- 判断の背景がリポジトリに残り、人間にも AI エージェントにも参照できる。
- 判断のたびに ADR を書く手間が増える。
- ADR は素の Markdown なので、特定のツールに依存せず他ツールへ移っても読める。

## 検証方法（任意）
- docs/adr/ に連番の ADR が存在し、各 ADR に Status が記載されていること。
- 設計判断を含む PR に、対応する ADR へのリンクがあること。
